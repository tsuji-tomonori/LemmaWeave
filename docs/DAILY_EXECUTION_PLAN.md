# LemmaWeaveの一周計画と日次実行

## 今回から固定する目標

2026年9月7日開始。日本時間の2・6・10・14・18時ごろに各10問、計50問/日を計画値とする。時刻は実行窓で、予約実行は前後1時間程度の幅を持つ。初回の7日間は処理速度を測る期間であり、50問/日は保証された実績ではない。

取得済みGSM8K固定版8,792問を一周する。行単位のLean対応が完了した3問を除き、旧形式5問の仕上げを含む8,789問が基準残件。50問/日なら176日、初期の完了予定日は **2027年3月1日**。日付を示す対象はこの固定集合であり、日本の全入試問題や高校数学全分野の終了日ではない。

| 節目 | 計画日 | 内容 |
|---|---|---|
| 開始 | 2026-09-07 | 5回の実行窓で初日50問を目標に処理 |
| 最初の100問 | 2026-09-08 | 2日分。原題を読んだ数ではなく解答検証が済んだ数 |
| 速度の見直し | 2026-09-14 | 完了数・持越数・失敗原因・所要時間を測り、完了見込みを補正 |
| 最初の1,000問 | 2026-09-26 | 20日分の計画値 |
| 固定集合を一周 | 2027-03-01 | 旧形式分の仕上げを含む。残件0なら完了 |

未実測の50問/日を約束と取り違えない。20問/日なら2027年11月20日、30問/日なら2027年6月26日になる。初期計画日は変更履歴として残し、実績に基づく見込み日と分けて表示する。

## 一周に必要な作業

| 順序 | 作業 | 完了の証拠 |
|---|---|---|
| 1 | 固定ソースの全ID・位置を台帳へ登録 | 全8,792行、重複0、固定splitの件数一致 |
| 2 | 前回の持越しと未完了から10問を選ぶ | `next_batch` の問題ID・担当実行・状態 |
| 3 | LLMが一問ずつ原文を読み、日本語の記述式解答を作る | 原題との対応、変数・条件・目標、作成者の自己照合 |
| 4 | 各行の根拠と使用条件を明示しLean定理にする | `individual_lines_v1` の各行と共有補題 |
| 5 | 固定Leanで実行し、根拠・公理・現在の入力を照合 | 成功CI、実行入力と出力のハッシュ |
| 6 | 解答・証拠・台帳・日報をGitHubへ保存する | commit/PR/CIへのリンク、当日完了数 |
| 7 | 失敗した問題は理由と次の一手を残し、他の問題を進める | 持越しID・実際のエラー・再開手順 |
| 8 | 一周後に共有公式を整理し、教材の依存順を整える | 重複補題の統合、未展開事項と分野不足の整理 |

中学既習は説明上の前提とする。独立レビューや全宣言の分類を解答の前提にしない。数値計算やキーワード規則で数学解答を自動生成しない。スクリプトは台帳・割当・検証・保存にだけ用いる。

## 毎回の実行

1. GitHubの最新mainと作業ブランチを確認する。作業ブランチのPRが未マージでも、その最新成果から続ける。既存の成果を待機状態に戻さない。PRがマージ済みなら最新mainから継続ブランチを作る。
2. `python3 scripts/solve_queue.py --write` で台帳と見込みを更新し、`reports/solve-progress.json` の `next_batch` を読む。既に完了したIDを再び解かない。
3. 持越しCIの結果を回収してから、原則10問を個別に解く。同じ誤りの再試行は4回を目安に切り上げ、難しい問題だけ持ち越す。目標未達なら件数を偽らず次回へ繰り越す。
4. `operations/daily/YYYY-MM-DD-<実行時刻>.json` に、対象ID、完了ID、持越し理由、開始終了時刻、CI/PR/commitを記録する。完了として報告する前に成功証拠を確かめる。
5. 日報・問題解答・進捗をpushする。新しいPRを毎回乱立させず、進行中の作業PRを継続する。他の更新をforce pushで上書きしない。
6. 各日の最後の実行で、その日の目標50問、実績、累計、残数、直近7日間の平均、更新後の完了見込みを報告する。0問の日や実行失敗も記録し、集計から消さない。

最初の実測見直し日は9月14日。日次ログが連続7日揃うまでは実測見込みを確定しない。7日間の完了が0なら完了日は「算出不能」とし、最初の失敗原因の修復を優先する。実行が抜けた日は0として速度に含める。予定日は試行数で前倒ししない。

## 分野を広げる作業

算数コーパスの消化だけで高校数学を網羅したとはしない。毎週、集合・整数、関数・方程式、図形・ベクトル、確率・統計、数列、微積分から各1問以上を選題・解答する追加目標を持つ。既存の公開問題台帳・出典候補から進め、見つけた問題を別コレクションへ追加する。未選題の枠は取得済み問題とは数えない。追加目標が未達なら明記する。

## 中断しても次回へ引き継ぐ

恒久的な再開情報はGitHubの本書、`operations/solve-plan.json`、全件キュー、日次ログ。scratchの同じパスが存在するとは仮定しない。必要ならリポジトリをcloneし直し、元データはmanifestの固定URL・commit・SHA256から再取得する。

接続切れ・利用上限・CI障害・実行時間制限は発生時に具体的に記録する。予約の登録は全回の実行成功を保証しない。外部障害があっても、すでに作った日本語解答とLeanの途中状態を保存し、次回の再開位置を明示する。

### 最初の週に確認・改善する実行基盤

| 作業 | 期限 | 判定 |
|---|---|---|
| 毎回の結果から10問/回を維持できるか測定 | 2026-09-14 | 実測時間、成功数、持越数を日報に保存 |
| 問題数増加に合わせ、変更した証明と影響する依存だけを再実行できるようにする | 2026-09-14 | 変更のない成功証拠を正しく再利用し、古い証拠を誤用しないテスト |
| 共通依存の重複保存と全件再走査の負荷を減らす | 2026-09-14 | 個別定理の公理・実依存の証拠を保ったまま保存量と時間を測定 |

現行の全件再実行方式のまま万問規模まで伸びるとは見込まない。この改善も最初の週の作業であり、未完なら50問/日の持続可能性は未確認と報告する。

試行を切り上げるときは日次JSONの `deferred` に `problem_id`・`retry_on`（次の再試行日）・`reason_ja` を保存する。キューはその日までは当該問題だけを選択から外す。残件数には残し、保留によって完了予定が前倒しされる扱いにはしない。
